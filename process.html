How I build things

I'm a nerd for data and design, so first and foremost, I think deeply about the problem. Most failed projects I've seen, at work and in my own builds, fail on the problem, not the code. So I write the problem down first, make the hard technical calls on paper, and only then start building, whether I'm writing the code myself or working with coding agents against that plan.

Write the PRD

The PRD states the problem, who has it, what success looks like, and a short requirements table with priorities, Must versus Later. It's rarely more than a page or two. The hardest part is always the same: deciding what's explicitly out of scope, so the build doesn't quietly grow past what the problem actually needs.

Produces: a one-to-three page PRD. Example: FlexFund

Design before building

For a personal tool, design means deciding what the interface should feel like before any component exists: a visual language, a few real screens, sometimes a rendered style guide I check against as I build. I don't user-test these the way I would at work; the real test is whether I actually want to open the thing every day.

Produces: wireframes and final screens. Example: MoveScape

Write the technical design

The technical design doc is the one document I hold every build agent to: the system shape, the data model, and an options table for each decision with a real trade-off, like choosing a computed field over an extracted one. If an agent hits an ambiguity the TDD doesn't answer, it stops and asks instead of guessing. The TDD also carries its own running change and status log, so a deviation from the plan gets written down with its reasoning right where the plan lives, instead of drifting quietly away from what's documented.

Produces: a technical design doc with an options table for each big decision. Example: taxsight

Build in small slices

I build using what I call the orchestrator model: a coordinator agent plans each phase against the spec, hands the work to a fresh builder agent, and reviews the output, including its unit tests, against acceptance criteria before I approve the next phase. Nothing moves on without its tests passing; that's usually where a bad assumption actually gets caught, not in a demo. Everything ships small and often, whether that means a milestone a day or, for the project I use every morning, a build session every time something real comes up.

Produces: working software, deployed early and often. Example: Oura Dashboard

Look back

Every project ends with an honest retro: what the plan got right, what it missed, and the bug that took too long to find. finsight's anomaly detector fired constantly in its first version, not because the data was wrong, but because I hadn't filtered out year-to-date values sitting next to true quarterly ones. That kind of finding is what keeps the next PRD from repeating the same mistake.

Produces: a short retro added to the project page. Example: finsight
