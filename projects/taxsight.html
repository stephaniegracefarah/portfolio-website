taxsight: tax obligations, extracted and cited

Solo project, in progress since March 2026

Problem
A marketplace operating in several countries picks up tax obligations from several unrelated regimes at once, each set by a different authority, published in a different format, and changed on its own schedule. Tracking that by hand means reading dozens of government and advisory pages and hoping nothing changed since the last time.
What I made
A pipeline that uses Claude to extract tax obligations from public regulatory sources into a structured, source-cited dataset, writes the results to versioned seed CSVs, and models them in dbt on DuckDB. Every row carries its source URL, a verbatim quote, and a confidence flag.
Where it is
Phase 1 in progress: 129 rows across four regimes for a first set of hero tickers, with public code.

Code on GitHub

The problem and the spec

A marketplace that operates in several countries picks up obligations from several unrelated regimes at once: seller reporting rules, digital services taxes, US state marketplace facilitator laws, and VAT and GST rules that make the platform the deemed supplier. Each regime is set by a different authority, in a different format, on its own schedule, and the guidance pages themselves move or disappear without notice.

The hardest scoping call showed up while validating the first set of hero tickers against a geographic segment disclosure policy. StubHub failed the check outright: its filings break out only the US, Switzerland, and a rest-of-world catch-all. The first replacement candidate, Uber, failed too, regional aggregates only, no individual countries beyond the UK. The one that actually passed was eBay, whose filings name the US, UK, Germany, and China individually. Real filings turned out to be pickier than the plan assumed.

Design

There's no interface to show here. The real design surface is the data itself: every row carries the same four audit fields (source URL, a verbatim quote, a confidence flag, a last-verified date) regardless of which regime it comes from, so a reviewer can trace any value back to the sentence that supports it without opening a second tab. Two of those fields were deliberate calls: the confidence flag exists because "the source is unclear" is a real, honest answer, not a failure state, and the verbatim quote exists because a paraphrase is one more place a value can quietly drift from what the source actually said.

Technical design

Two ETL strategies run side by side. Scrape mode fetches one authoritative page, strips it to text, and passes it to Claude with a regime-specific prompt: extract only what's explicitly stated, return null for anything missing, include a verbatim quote. Research mode gives Claude a country and the web search tool instead, since VAT and GST marketplace rules are fragmented across 34 national tax authorities and no single source covers them. Scrape mode is preferred whenever a single authoritative source exists, since the source is fixed and easy to verify; research mode trades some of that control for coverage.

Extracting the complexity score, or computing it

Option Why it was attractive Why I didn't pick it
Ask Claude to extract the complexity score directly, alongside the other fields One extraction pass, no separate scoring logic to write and maintain There's nothing in any source to extract; it's a taxsight methodology choice, not a fact. Asking Claude to extract it anyway contradicted the project's own rule, never infer values not in the source, and produced numbers with no traceable basis
Compute it deterministically in each build script, chosen The same inputs always produce the same score, and the rule is identical across all four regimes One more computed field to keep in sync across four separate build scripts instead of one shared extraction prompt

Stack: Python, Anthropic Claude API (web search tool), requests, BeautifulSoup, dbt Core, DuckDB.

Building and launching

Phase 1's data build happened in about three days in March 2026: scaffolding and dbt setup, then the ETL scripts and prompts, then the seed data itself. The six-month gap after that wasn't idle time, it was a deliberate pause. Scraping commercial sites like Avalara raised a real question worth stopping for, even for a non-commercial personal project: whether that was actually the right source to lean on, licensing and authority both considered. The resolution, replacing the Avalara marketplace facilitator and economic nexus sources with primary state department of revenue sources, is now the top item in the Phase 1 roadmap, and it's the reason that regime doesn't have a staging model and dbt tests yet either. That work is waiting on the source swap, not stalled by accident.

The most durable lesson from Phase 1 wasn't a code bug, it was that government URLs move without warning. All three original source URLs for DAC7, UK DPI, and Canada DPI returned 404 partway through the build. I found the current pages by hand and updated the scripts, and URL validation is now a permanent manual step in the quarterly refresh checklist rather than an assumption baked into the extraction scripts.

Looking back

The marketplace facilitator thresholds needed a second source before they were actually usable: the primary guide simply doesn't state a revenue threshold for eight states, and the fix was adding a second source plus a merge function that only fills gaps and never overrides the primary source when the two might mean different things. What I'd flag honestly: the VAT and GST rows come from Claude's own web search rather than one fixed authoritative page per country, which is the right call for coverage but a real trade-off in verifiability against the scraped regimes, and it's the one place in the dataset I'd want a second reviewer before trusting a row at face value.
