The brief I hand a build team

Excerpt from the FlexFund build, 2026. Trimmed and redacted

FlexFund was built by four coding agents, each with a scoped role, run by a fifth agent that never writes code. This is the document that defines them and the rules the orchestrator follows. It is the working file from the private repo, cut down to the parts that show how the build was controlled, with personal details removed.

Read the FlexFund case study

The rule everything hangs on

The brief opens with one sentence: the technical design is the law. If any agent hits an ambiguity or needs to deviate, it stops immediately, proposes a changelog entry describing the deviation and why, and surfaces it to the orchestrator for approval before implementing anything.

Seven universal rules sit under it and apply to every agent.

Universal rules
Read the full technical design before writing any code.
Never implement anything outside your defined scope.
Never make a design decision that is not in the technical design. Flag it instead.
Every file you create or modify goes in your output manifest.
If a previous agent's output contradicts the technical design, flag it. Do not silently work around it.
Leave a comment in the code wherever an assumption was made.
Confirm completion with a fixed sentence: "Checkpoint [N] complete. Ready for Orchestrator review."

Four agents, four scopes

Each agent gets a checkpoint, a scope, and an explicit list of what it does not do.

Agent and checkpoint Owns Does not do
Architect, checkpoint 0 The project scaffold, login, route protection, and the first deploy Fetch any data, build UI beyond login and a blank shell, or write database functions
Data layer, checkpoint 1 TypeScript types for every row, query and mutation hooks, cache invalidation on every write Build UI, modify database functions, or format money
UI builder, checkpoints 2 and 3 The paycheck card stack, check-off, inline editing, and adding obligations Modify hooks or the data layer, or build the later trends screen
QA and polish, checkpoint 4 Adversarial validation against the design, installability, and a pass or fail report Add features, or fix bugs directly. Failures go back to the orchestrator with reproduction steps

The "does not do" column is as important as the scope. It is what keeps one agent from quietly redesigning another agent's work.

What a system prompt looks like

Every agent gets a prompt with the same shape: the job, the facts it must not re-derive, what to produce, and a check it has to run itself before reporting back. This is an excerpt from the data layer agent.

Data layer agent, excerpt

Your job is to create the TypeScript types and React hooks that connect the frontend to the backend. The database functions are already deployed and returning real data. Your hooks must call them correctly and handle loading and error states.

Key facts. All money is integer cents. Do not format to dollars in hooks. Dates come back as strings from the RPC, so type them correctly. A payment record is keyed by source type, source id, and due date.

Confirm: log both query hooks' results in the browser console with real data. Output a manifest.

The key facts paragraph carries decisions already made on paper, so the agent does not make them again.

The QA agent is told to be adversarial

The last agent's prompt says it runs last, that its job is to validate the deployed app against the technical design, and that it is adversarial: it is there to find failures. It works from a numbered checklist of fourteen criteria, and some are deliberately specific, for example that a bill named "Cat Food" shows its merchant, Chewy, while one named "Rocket Money" does not, because the merchant is already in the name.

For each criterion the report says pass or fail. For each fail it gives reproduction steps and expected versus actual behavior, and returns them to the orchestrator. The QA agent does not fix what it finds. Whoever finds the bug is not the one who fixes it.

The orchestrator's rules

The orchestrator is also an agent, and its instructions begin by saying it does not write implementation code. It sequences agents, reviews checkpoints, and maintains the build state in a single running file.

# Rule
1Brief each agent with its scoped instructions and the correct inputs.
2Review each checkpoint against the technical design's acceptance criteria and the agent's output manifest.
3Never pass a failing checkpoint. Return it to the agent with specific failure notes.
4Log everything. Every deviation, decision, or clarification goes in the changelog.
5Do not write implementation code. Sequence, review, and decide.
6If an agent hits an ambiguity, it stops and surfaces it. The orchestrator decides, logs the decision, and adds it to the key decisions.
7The technical design is the law. An agent that wants to deviate proposes a changelog entry, and the orchestrator approves or rejects it.
8Update the build state after each checkpoint is approved.
9At the end of each session, update the session notes with what was completed, what is next, and any context the next session needs.

Rule 9 exists because every session starts with an agent that remembers nothing. The file is the memory.
