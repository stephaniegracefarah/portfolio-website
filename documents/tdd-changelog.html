How a spec changes when it meets real data

Excerpt from the FlexFund technical design and its running log, 2026. Condensed and redacted

FlexFund's earlier design had plan and lock states, snapshots, and a planned-versus-actual comparison. Then I built the database layer with my real data, about 42 recurring expenses, real income, and real debts, and the model did not hold up. Version 3 is what remained. The changelog sits at the top of the document, so the reasons for a change travel with the plan itself.

Read the FlexFund case study

Changelog, version 2.0 to 3.0

These changes came from pressure-testing the model with real data. Together they are a fundamental simplification of the architecture. The wording here is condensed from the original.

# Change What it replaced or removed
1 The app is a living projection the user updates as reality happens. Edit a template and the whole future recalculates. Check off a bill and it records what was actually paid. The entire plan and lock state machine: no locking, no snapshots, no planned versus actual, no dual chains
2 One rollover chain, always live. The paycheck plan table, dropped because there are no snapshots to store
3 Fund Future Periods: an automatic reserve line in each paycheck where money is needed for a later deficit. The old rollover line. Every dollar now has a deliberate job
4 Flex Fund: the truly free money, defined as the minimum the running balance ever hits across the remaining horizon. It is the app's core metric and its name. The old "unassigned" and "to allocate" concepts
5 The schedule engine runs in Postgres. Two functions, the ledger and the paycheck summary, are all the app calls. The client is a thin renderer. Schedule logic in client-side JavaScript
6 One income line. The savings transfer is tracked as a "Fund Myself" expense. Separate income lines for each deposit account
7 New expense fields: variable amount, autopay, and hidden notes revealed on tap. Nothing removed. These are additions
8 Balance snapshot deferred. The MVP starts at zero plus the first paycheck's income. A "start over" flow comes after. The balance snapshot in the MVP
9 Build phases dramatically simplified. The phases needed only for locking, snapshots, and dual chains

The original has ten items. Dropping the paycheck plan table and moving to a single chain are merged into row 2 here.

Three hard rules

Right under the changelog, a short "how to read this document" section names the rules a builder cannot break. It also says to build in order, and that every phase has an acceptance check: do not advance until it passes.

# Rule
1The schedule is derived, never stored. Occurrences are computed from a start date and a cadence. Writing a row for "expense X on date Y" is a bug.
2One living projection. There is no planned versus actual split. Recurring templates define the projection, and payment records only record what actually happened.
3Nothing before the seed paycheck exists. The app is forward-only.

Ten invariants

An appendix at the end of the technical design lists the invariants: the things that must stay true whatever else changes.

# Invariant
1No occurrence is ever written to the database. Occurrences are derived by the ledger function.
2All money is integer cents end to end. Dollars exist only at the display formatter.
3One rollover chain, always live. No dual planned and actual chains.
4Fund Future Periods is the end balance minus the larger of the future balance floor and zero. It appears only when it is greater than zero.
5Flex Fund is the larger of zero and the lowest end balance from this paycheck forward. It is the core metric.
6Editing a template changes the projection on the next query. No locking, no confirmation.
7A payment record is purely a record of what happened. It does not affect the projection.
8Nothing before the seed paycheck is ever rendered or queried.
9One payment record per source and due date.
10The base line generator is internal. The app calls only the ledger and paycheck summary functions.

The log after the spec

The spec is not finished when the build starts. The orchestrator's file carries a running changelog, and any deviation from the design is written down there with its reasoning. Three entries from the first two days:

Date Entry Why it matters
2026-06-02 Merchant display through a client-side map. The ledger function returns the expense name but not the merchant. Rather than modify the deployed database function, merchant data is fetched separately from the expense table (id, name, and merchant only) and joined in the client by source id. No database change required. The deployed database function was left untouched instead of being changed mid-build
2026-06-03 Fix for PWA installation. On Android, Chrome offered "Add to Home Screen" instead of "Install app." Root cause: the route-protection middleware did not exclude the service worker and the manifest. Chrome's background installability check fetches those files without a session, got redirected to the login page, received HTML instead of JSON and JavaScript, and could not confirm the app was installable. The fix excluded those files from the matcher and tightened the manifest. Confirmed on a real phone. The root cause was found by looking at what the browser actually received
2026-06-03 Security review. A full audit of auth, hooks, database functions, components, and config found no high or medium issues. Three low findings were fixed: generic error messages in place of raw database errors, a non-negative check on all five money columns because a valid session could bypass client-side validation with a direct API call, and a config file added to the ignore list. The database constraint exists because the client check alone was not enough

Each entry in the log states the decision, the reason, and what changed.
